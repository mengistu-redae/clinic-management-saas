# API Reference

Complete reference of every REST endpoint exposed by `spring-boot-api`. Generated by reading every `*Controller.java` file under `spring-boot-api/src/main/java/com/clinicops/` directly against the running codebase (not reconstructed from memory) — accurate as of migration `V29`.

## Conventions

- **Base URL**: every endpoint is mounted under `/api/...` (plus one health check at `/actuator/health` and Spring Boot's own `/error`). The browser never talks to this service directly — it goes through `node-bff`, which proxies everything under `/api/*` and attaches the session's access token as a `Bearer` header. `spring-boot-api` itself is reachable directly on `:8081` only for local debugging.
- **Format**: every request/response body is JSON (except two binary endpoints, called out explicitly: a provider's signature image and an invoice/visit-summary PDF).
- **Auth**: a Bearer JWT, issued by Keycloak, validated by Spring Security on every request. The browser itself never holds or sends a token — only `node-bff`'s session cookie. A handful of endpoints are genuinely public (`permitAll()` in `SecurityConfig` **and** listed in `node-bff`'s own `PUBLIC_ROUTES`, confirming they're reachable pre-session through the real browser-facing path, not just at the Spring Security layer) — those are marked **public** below; everything else requires a valid session.
- **CRUD shape**: this codebase's standard pattern is `GET` (list) / `GET {id}` (one) / `POST` (create) / `POST {id}/update` (partial update) — there is no `PUT`, `PATCH`, or bare `DELETE` verb anywhere in this API. A few resources use a real hard delete, always as `POST {id}/delete` or `POST {id}/remove` — each one is called out explicitly where it appears, since most resources in this app soft-deactivate via a `status` field instead.
- **Role-gate legend**: a bare role name (e.g. `clinic_admin`) means `hasRole(...)`; multiple roles joined by `+` (e.g. `clinic_admin + front_desk`) means `hasAnyRole(...)` — any one of them is sufficient, not all of them. **public** means `permitAll()` — reachable with no session at all, confirmed against both `SecurityConfig` and `node-bff`'s `PUBLIC_ROUTES`.
- **Tenancy**: every staff-scoped endpoint resolves the acting clinic from `TenantContext` (derived from the JWT's `organization` claim via `TenantContextFilter`), never from a client-supplied tenant id — cross-tenant access attempts return `404`, not `403`, to avoid confirming a resource exists in another tenant.

## Accounting (`com.clinicops.accounting`)

`accountant`+`clinic_admin` only throughout. `AccountController` lazily seeds a tenant's starter chart of accounts (Cash/Service Revenue/Refunds & Allowances/Salary Expense) the first time `GET /api/clinic/accounts` is called. `JournalController` is read-only — the ledger itself is only ever written by `JournalService`'s own auto-posting against a real `Payment`/`Refund`/payroll run, never through a request body.

|---|---|---|---|

| GET | `/api/clinic/accounts/{id}` | accountant + clinic_admin | One account. |
| POST | `/api/clinic/accounts` | accountant + clinic_admin | Create (rejects a duplicate `code`). |
| POST | `/api/clinic/accounts/{id}/update` | accountant + clinic_admin | Partial update — name/status only; `code` is fixed at creation (`JournalService` resolves starter accounts by code). |

| GET | `/api/clinic/trial-balance` | accountant + clinic_admin | Running debit/credit totals per account, signed by the account's own debit-/credit-normal type. |

## Invoices (`com.clinicops.invoice`)

Three controllers sharing one `Invoice` entity and `InvoiceService`/`InvoicePdfService`, split only by owner type (appointment/dispense-record/lab-order) and base path. Generating an invoice is always a deliberate, separate staff action — never an automatic side effect — and every invoice is immutable once issued (a second `POST` on the same owner 409s). PDFs are rendered on demand, never persisted.

| Method | Path | Role(s) | Description |

| GET | `/api/dispense-records/{id}/invoice` | front_desk + clinic_admin + pharmacist | A dispense's invoice — `pharmacist` gets full read+write here (not read-only like `provider` on the appointment owner above), since pharmacist is the real counter-staff role for a pharmacy sale. |

## Payments (`com.clinicops.payment`)

Three owner-specific controllers (appointment/dispense-record/lab-order) sharing one `Payment` entity/`PaymentService`, plus one owner-agnostic `PaymentController` for refunds (addressed by the payment's own id, never nested under an owner path). Every payment routes through `PaymentGatewayClient` (mock-only today) and gains a `gatewayTransactionId`/`gatewayStatus`. No delete anywhere in this package.

| Method | Path | Role(s) | Description |
|---|---|---|---|
| GET | `/api/appointments/{id}/payments` | front_desk + clinic_admin + provider | Payments recorded against an appointment. |
| POST | `/api/appointments/{id}/payments` | front_desk + clinic_admin | Record one (optionally linked to that appointment's own already-issued invoice). |
| GET | `/api/dispense-records/{id}/payments` | front_desk + clinic_admin + pharmacist | Payments against a dispense — `pharmacist` full read+write, same phase-31 widening as the Invoices section above. |
| POST | `/api/dispense-records/{id}/payments` | front_desk + clinic_admin + pharmacist | Record one. |
| GET | `/api/lab-orders/{orderId}/payments` | front_desk + clinic_admin + provider | Payments against a lab order. |
| POST | `/api/lab-orders/{orderId}/payments` | front_desk + clinic_admin | Record one. |
| GET | `/api/payments/{id}/refunds` | front_desk + clinic_admin + provider | Refund history for one payment. |
| POST | `/api/payments/{id}/refund` | front_desk + clinic_admin | Full or partial refund — **deliberately not opened to `pharmacist`**, even though it can refund a dispense payment, since this endpoint is owner-agnostic and would also let a pharmacist refund an appointment/lab-order payment. |

## Pharmacy (`com.clinicops.pharmacy`)

`pharmacist`+`clinic_admin` throughout on every staff endpoint — no other staff role has pharmacy access, except the two deliberately-widened read-only exceptions called out below. Dispensing a controlled substance never goes through the plain one-step `dispense` endpoint — it's routed through `ControlledSubstanceDispenseController`'s own two-phase, two-signer workflow instead.

| Method | Path | Role(s) | Description |
|---|---|---|---|
| GET | `/api/pharmacy/controlled-substance-requests?status=` | pharmacist + clinic_admin | Pending/cosigned/rejected controlled-substance dispense requests. |
| POST | `/api/prescriptions/{id}/controlled-substance-requests` | pharmacist + clinic_admin | Request a controlled-substance dispense (400 if the medication isn't actually controlled). |
| POST | `/api/pharmacy/controlled-substance-requests/{id}/cosign` | pharmacist + clinic_admin | Co-sign and finalize — must be a genuinely **different** person than the requester (409 otherwise, enforced in the service layer, not the role gate). |
| POST | `/api/pharmacy/controlled-substance-requests/{id}/reject` | pharmacist + clinic_admin | Reject — no stock ever touched, since none was decremented at request time. |
| GET | `/api/pharmacy/queue` | pharmacist + clinic_admin | Active prescriptions not yet fully dispensed, each with a suggested catalog medication (simple bidirectional substring match, not real fuzzy matching). |
| GET | `/api/prescriptions/{id}/dispense-records` | pharmacist + clinic_admin | A prescription's own dispense history. |
| POST | `/api/prescriptions/{id}/dispense` | pharmacist + clinic_admin | Dispense against a specific stock batch — 400 if this medication is controlled (use the controlled-substance flow instead); checks allergy/interaction conflicts first, requiring explicit acknowledgment to proceed past one. |
| GET | `/api/pharmacy/drug-interaction-pairs` | pharmacist + clinic_admin | The interaction pairs checked during dispensing. |
| GET | `/api/pharmacy/drug-interaction-pairs/{id}` | pharmacist + clinic_admin | One pair. |
| POST | `/api/pharmacy/drug-interaction-pairs` | pharmacist + clinic_admin | Create (rejects a self-pair and a duplicate in either order). |
| POST | `/api/pharmacy/drug-interaction-pairs/{id}/update` | pharmacist + clinic_admin | Update severity/description — the two medications themselves are fixed at creation. |
| POST | `/api/pharmacy/drug-interaction-pairs/{id}/delete` | pharmacist + clinic_admin | **Hard delete.** |
| GET | `/api/clinic/medications?status=` | pharmacist + clinic_admin + front_desk | The medication catalog — `front_desk` read-only, added so it can pick a medication when placing a purchase-order line. |
| GET | `/api/clinic/medications/{id}` | pharmacist + clinic_admin + front_desk | One medication. |
| POST | `/api/clinic/medications` | pharmacist + clinic_admin | Create. |
| POST | `/api/clinic/medications/{id}/update` | pharmacist + clinic_admin | Partial update, incl. status. |
| POST | `/api/clinic/medications/{id}/controlled-substance-schedule` | clinic_admin | Dedicated action endpoint, **tighter** than the catalog's own gate — sets/clears the controlled-substance schedule. |
| GET | `/api/clinic/medications/{id}/stock-batches` | pharmacist + clinic_admin | A medication's stock batches, **FEFO-sorted** (earliest expiry first) — a sort, not an automatic pick. |
| POST | `/api/clinic/medications/{id}/stock-batches` | pharmacist + clinic_admin | Receive a new batch. |
| POST | `/api/clinic/medications/{id}/stock-batches/{batchId}/write-off` | pharmacist + clinic_admin | Zero a batch out as expired/recalled. |
| GET | `/api/my-prescriptions` | patient | The caller's own prescriptions, with dispensed-so-far progress. |
| POST | `/api/my-prescriptions/{id}/refill-requests` | patient | Request a refill (400 if the prescription isn't `active`, 409 on a second pending request for the same one). |
| GET | `/api/my-refill-requests` | patient | The caller's own refill requests. |
| GET | `/api/pharmacy/refill-requests?status=` | pharmacist + clinic_admin | Staff review queue, with patient/medication names embedded directly. |
| POST | `/api/pharmacy/refill-requests/{id}/approve` | pharmacist + clinic_admin | Approve — sends a real "refill ready" email if the patient has one on file. |
| POST | `/api/pharmacy/refill-requests/{id}/deny` | pharmacist + clinic_admin | Deny with a reason — sends no notification. |
